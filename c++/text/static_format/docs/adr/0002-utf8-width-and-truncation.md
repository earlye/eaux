# Width, precision and `to_n` are grapheme-aware UTF-8 in both syntaxes

All text is treated as UTF-8, and the unit of truncation and width is the extended grapheme
cluster (UAX #29), as in `std::format`. Field width counts display width (the standard's
wide-character ranges count 2). String precision never splits a grapheme. `to_n` stops at the
last complete grapheme that fits while still returning the untruncated size. This applies to
`_pfmt` too, deliberately departing from C `printf`'s byte counting, so that tabular output with
labels like `µ`, `σ_max` or a combining accent stays column-aligned and never loses part of a
character.

A cluster can span a literal and an argument (`"e%s"` with a combining accent), so `to_n`
formats the whole output, which it must measure anyway for the untruncated size, and cuts that
at the last cluster boundary that fits. Runtime strings are scanned up front for any byte >= 0x80,
a branch-free word-wise OR that the compiler can vectorize. ASCII strings take a fast path where
length equals width and any cut is valid except between CR and LF. Only non-ASCII strings walk
graphemes. Malformed UTF-8 passes through unchanged.
`eaux::text::ascii_string_view` is a validated type that carries the ASCII guarantee: it validates once at
construction (`consteval` from a `_ascii` literal; `ascii_string_view::from(sv)` returns
`std::expected<ascii_string_view, std::size_t>` with the offset of the first byte >= 0x80), and
formatting selects the ASCII emitter for it at compile time with no scan. `%{ascii}s` makes the
validated type a compile-time requirement for that argument; it is not a runtime refusal, so formatting
stays infallible at runtime. The segmentation, width and scan code, and the Unicode property tables, live in
`eaux::text::unicode` (`c++/text/unicode`); the tables are generated by a script in that package into a checked-in header, pinned to one Unicode version, and tested
against `GraphemeBreakTest.txt`. The build assumes UTF-8 source and literal encoding (`/utf-8`
on MSVC).

## Considered Options

- Byte counting in `_pfmt` for exact `sprintf` fidelity, Unicode awareness only in `_bfmt`.
  Rejected: columns misalign as soon as a label leaves ASCII.
- Code-point granularity with no tables. Rejected: a cut can drop a combining accent and leave
  the wrong letter.
- A switch for a single-byte mode. Rejected as redundant with the ASCII fast path.
- `%{utf:false}s` refusing non-ASCII at format time. Rejected in favour of the validated type: a
  format-time refusal needs a runtime error channel the library otherwise lacks.
